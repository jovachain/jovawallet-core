# Design Decisions

Short ADRs (Architecture Decision Records) for the load-bearing choices behind `jovawallet-core`. Each entry is decision + rationale + alternatives considered + revisit-condition.

ADRs are append-only. When a decision changes, add a new ADR that supersedes the old one rather than rewriting history. The point of these is so a future engineer (or auditor) can understand *why* a choice was made even if the choice has since been overturned.

---

## D1: Engine is pure-Rust crypto crates, not Trust Wallet Core

**Decision.** All cryptographic and chain-specific signing logic in `jovawallet-core` is implemented on top of audited pure-Rust crates: `bdk_wallet` (BTC), `alloy` (EVM), Anza's split Solana crates (`solana-keypair`, `solana-transaction`, `solana-message`, `solana-pubkey`, `solana-signature`), `xrpl-rust` (XRP), and `rust-bitcoin/rust-secp256k1` + `ed25519-dalek` + `bip39` + `slip-10` for primitives.

**Alternative considered: wrap Trust Wallet Core.** Rejected.

- TWC is C++ (mid-migration to Rust); there is no first-class `walletcore-rs` crate on crates.io. Community usage is via `bindgen` against TWC's auto-generated C headers.
- TWC depends on `std`, dynamic dispatch, protobuf, and a C++ runtime. It cannot run on hardware-wallet firmware. Since hardware-wallet support is on our roadmap, choosing TWC means committing to a future migration anyway.
- TWC's WASM build is beta with low usage (~1.5k weekly npm downloads).
- For the four chains we support at v1, the pure-Rust crates are equal-or-better quality. BDK is the Bitcoin standard. Alloy is the current EVM standard (`ethers-rs` is deprecated). Anza's split Solana crates are first-party (and replace the monolithic `solana-sdk` because the split versions are WASM-viable and have a much smaller dep tree). `xrpl-rust` was funded by an XRPL Foundation grant.

**Rationale.**

- One crypto implementation, not two language-specific ones.
- Native portability to every platform we want to ship to: iOS, Android, web (WASM), desktop, backend, hardware (`no_std`).
- Smaller dependency surface than TWC. Each crate is independently auditable.
- Industry pattern: this is what Block's Bitkey, Foundation Devices' Passport, and the BDK ecosystem do.

**Revisit when.** A chain we need to support has no production-quality pure-Rust crate and only ships in TWC. (Not currently anticipated for any chain on our 3-year roadmap.)

## D2: Single repo, one Rust workspace, multiple binding outputs

**Decision.** `jovawallet-core` is one GitHub repo containing a `crates/` directory (Rust workspace) and a `bindings/` directory (Swift/Kotlin/WASM packaging).

**Alternative considered: separate repos per binding.** Rejected because nothing forces them to stay in sync. Drift between Swift and Kotlin signing behavior is the primary risk this whole project is designed to prevent.

**Alternative considered: monorepo with two parallel native implementations (the previous draft of this ADR).** Rejected when ADR D3 was overturned.

**Rationale.**

- One place to file an issue, one place to land a fix, one CI run that validates every binding.
- `spec/test-vectors.json` literally sits in the same git tree as the implementations that must pass it.
- Releases are tagged once and produce every artifact (crates.io, SwiftPM satellite repo, Maven Central, npm) from the same commit.
- The Swift-side satellite repo is auto-pushed by CI; humans never edit it directly.

**Revisit when.** Any binding's release pipeline becomes complex enough that splitting it out would simplify operations more than it would create drift risk. Not foreseeable.

## D3: Rust core with `uniffi-rs` and `wasm-bindgen` bindings, not language-native wrappers

**Decision.** Implementation is one Rust workspace. Swift and Kotlin bindings are auto-generated by `uniffi-rs`. JavaScript/WASM binding is auto-generated by `wasm-bindgen`. There is no hand-written Swift or Kotlin signing code.

**Alternative A: Two thin native wrappers around TWC** (the previous draft of this ADR). Rejected because:

- It makes hardware-wallet support effectively a from-scratch rewrite — TWC doesn't run on firmware.
- It commits us to two implementations of the public API forever, with the drift risk the test vectors are mitigating but not eliminating.
- WASM and desktop bindings would each need their own wrapper, growing the maintenance surface to N implementations.

**Alternative B: Kotlin Multiplatform shared module + Rust crypto via JNI/uniffi.** Rejected for v1. KMP is Bitkey's pattern, but Bitkey's KMP shares non-crypto code (Compose UI, business logic). ADR D7 locks `jovawallet-core` to signing primitives only — there is no non-crypto code to share. KMP also has a weak hardware-wallet story and beta-quality Kotlin/Wasm.

**Alternative C: Hand-rolled FFI (cbindgen + manual Swift/Kotlin wrappers).** Rejected. `uniffi-rs` does this for us, generates idiomatic types in each language, handles error mapping, and has Mozilla-scale production usage.

**Rationale.**

- Single source of crypto truth.
- Idiomatic API in every language (Swift `enum` with associated values, Kotlin sealed classes, JS `class`).
- BDK's `bdk-ffi` repo is the canonical template — production, MIT-licensed, exact same shape as ours.
- Auto-generated bindings track the Rust API automatically; adding a method on the Rust side appears in Swift and Kotlin without any binding-side code change.

**Revisit when.** `uniffi-rs` becomes unmaintained, *or* a target platform requires bindings `uniffi-rs` doesn't generate. Mozilla actively maintains it; this is not currently a risk.

## D4: Bitcoin uses BIP-84 (native SegWit, `bc1q…`) at v1; BIP-86 (Taproot) added when ready

**Decision.** All BTC derivation in `jovawallet-core` uses BIP-84 — `m/84'/0'/0'/0/n`, P2WPKH, bech32 addresses.

**Alternative considered.** BIP-44 (`m/44'/0'/0'/0/0`, P2PKH `1…`). Rejected — legacy. Modern wallets default to native SegWit (lower fees, smaller signatures, broad node support).

**Migration cost.** The legacy iOS app derived `1…` addresses but had no signing path — no user funds were ever sent to one. The legacy Android app already uses BIP-84. So unification is *toward* BIP-84 with no real migration cost.

**Taproot (BIP-86, P2TR `bc1p…`).** Will be added as a separate `JovaChain.bitcoinTaproot` variant when descriptors and PSBT-v2 use stabilizes in our backend. BDK supports Taproot fully; the limiter is backend PSBT construction, not the SDK.

**Revisit when.** Industry consensus moves fully to Taproot (Lightning, Ark, etc. drive this). We add `JovaChain.bitcoinTaproot` and migrate `bitcoin` after a major-version bump.

## D5: Plain language types at the API boundary, no engine types in public

**Decision.** No file outside `jova-core-chains` references `bdk_wallet`, `alloy`, the Solana split crates, `xrpl-rust`, or any other underlying crypto crate. The public API in `jova-core` exposes only plain Rust types: strings, byte arrays, plain enums, plain structs, `thiserror`-derived errors. `jova-core-ffi` and `jova-core-wasm` re-export only those.

**Rationale.**

- Apps cannot become accidentally coupled to engine types. A future migration of any chain's underlying crate is a one-file change in `chains::<chain>`.
- Easier to read and document — no upstream type conventions leaking into the public surface.
- Easier to audit — the public contract is small and inspectable.

**Revisit.** Never. This is a load-bearing invariant.

## D6: Distribution via crates.io (Rust) + SwiftPM (iOS) + Maven Central (Android) + npm (web)

**Decision.**

- Rust consumers add the crates from `crates.io`.
- Swift consumers add `JovaCore` via SwiftPM, pinning a tag of the satellite repo `jovachain/jovawallet-core-swift`.
- Android consumers add `io.jovachain:jova-core` from Maven Central.
- Web consumers add `@jovachain/wallet-core` from npm (Phase 6).

**Alternative for iOS: CocoaPods.** We will ship a `JovaCore.podspec` for compatibility with old iOS app consumers, but SwiftPM is the canonical channel.

**Why a satellite Swift repo.** SwiftPM resolves better when `Package.swift` sits at the root of its own repo; this is BDK's pattern and Apple's best practice for binary-target packages. CI pushes the satellite repo automatically on every tag — humans never commit to it directly.

**Revisit when.** A future Apple change to SwiftPM lets monorepo `Package.swift` files resolve as cleanly as root-of-repo ones. Likely never.

## D7: Out of scope is locked

**Decision.** `jovawallet-core` does not do RPC, fee estimation, balance fetching, transaction history, secret storage, biometrics, PIN, WalletConnect protocol, or UI. Ever. Future modules will cover these (`jova-fees`, `jova-rpc`, `jova-wallet-ui`); they live in their own repos when they exist.

**Rationale.**

- Keeps the audit surface small.
- Keeps the API stable — every new method is forever, so adding fewer matters.
- Lets backends and apps evolve independently of the SDK.

**Revisit.** Never. If new functionality is genuinely shared between platforms, it goes in a new module — never this one.

## D8: Lockstep versioning across all bindings

**Decision.** Every artifact published at a Git tag `vX.Y.Z` is built from the same commit. There is no scenario where Swift sits at `1.4.2` and Kotlin at `1.4.3`. The CI release workflow enforces this — all artifacts publish or none do.

**Rationale.**

- Drift between bindings of different versions is the failure mode this whole project exists to prevent.
- App teams reading `jova-core 1.4.2` documentation can trust that the iOS and Android packages tagged `1.4.2` are identical in behavior.
- A new chain or method appears in every binding at the same release.

**Revisit.** Never.

## D9: Layered crates with one-way dependencies

**Decision.** The Rust workspace is layered: `primitives` ← `chains` ← `core` ← `ffi` / `wasm`. Dependencies flow only upward through this list. `cargo-deny` enforces this in CI.

**Rationale.**

- `jova-core-primitives` is `no_std`-clean and lands on hardware-wallet firmware. Letting it depend on a `std`-using crate would break that.
- The layering also produces sensible compilation-unit boundaries that let us test the primitives in isolation without dragging in chain-specific crates.

**Revisit when.** A genuinely useful primitive needs chain-specific knowledge. If that happens, the design is wrong — re-examine the boundary.

## D10: Async is a binding-layer concern, not a core concern

**Decision.** `jova-core` is sync-only. No `async fn`, no `tokio`, no futures. The public API methods are blocking calls.

**Rationale.**

- Signing is fast (microseconds to single-digit milliseconds) — async is not load-bearing for performance.
- Async leaks into bindings: an `async` Rust API forces Swift `async` and Kotlin `suspend`, which is fine, but also forces a runtime choice that complicates `no_std` and WASM compilation.
- Bindings that *want* async wrap the sync call in a platform-appropriate background dispatch. iOS uses GCD or `Task.detached`; Android uses `Dispatchers.Default`; the JS binding can offload to a Web Worker.

**Revisit when.** A signing operation we add takes long enough that blocking the calling thread becomes a UX problem (e.g., a future ZK-proof-based chain). Even then, the right answer might be "wrap the sync call in an async layer at the binding," not "make core async."

## D11: Secret memory is `zeroize`-managed in Rust; bindings extend the contract within language limits

**Decision.** Every type in `jova-core-primitives` and `jova-core` that holds secret material (mnemonic words, seeds, private keys, signature work buffers) implements `zeroize::Zeroize` and is wrapped in `Zeroizing<T>` at construction sites. `Drop` clears the underlying memory.

Across the FFI:

- **Swift** wraps the native handle in a `final class` whose `deinit` calls a Rust-side `clear()`. Swift `String` is opaque to us — apps must use the `MnemonicBuffer` byte-array variant if they need clearing guarantees on the input string.
- **Kotlin** types implementing `AutoCloseable`. Apps `use { … }` (Kotlin's try-with-resources) to bound the lifetime; explicit `close()` on the wallet zeroizes the underlying handle. Kotlin `String` has the same JVM-level immutability problem as Swift `String`; the same `MnemonicBuffer` escape hatch applies.
- **JavaScript** has no real way to zero memory. The binding documents this honestly: WASM linear memory holding the seed is cleared on `JovaWallet.destroy()`, but anything the JS host has copied is in the GC's hands. Web consumers should treat their environment as a soft-secret zone and rely on Keychain-equivalent storage (browser `WebAuthn` PRF, OS keystores via native helpers) for durable secrets.

**Rationale.** Honest contract. We provide the strongest guarantees the platform allows and document the gaps clearly.

**Revisit when.** A standardized cross-platform secure-memory primitive emerges. (None on the horizon.)

## D12: One `ChainSigner` trait, one impl per chain family

**Decision.** Inside `jova-core-chains`, every chain family implements the same trait:

```rust
pub trait ChainSigner {
    fn derive_address(&self, key: &XPrv, account: u32) -> Result<Address, JovaError>;
    fn validate_address(&self, addr: &str) -> bool;
    fn sign_tx(&self, key: &XPrv, unsigned: &UnsignedTx) -> Result<SignedTx, JovaError>;
    fn sign_message(&self, key: &XPrv, msg: &SignableMessage) -> Result<Signature, JovaError>;
}
```

A `JovaChain` value dispatches to its `ChainSigner` implementation through a `match`, not through dynamic dispatch — keeping the binary smaller and avoiding `dyn` on the hot path.

**Rationale.** Adding a chain becomes a checklist: implement the trait, register in the dispatch, add vectors. The trait makes "what does a new chain need to provide?" answerable in 30 seconds.

**Revisit when.** A chain's needs (e.g., requiring a deterministic nonce that the SDK has to track) demand storage that doesn't fit the trait. So far no chain we'd consider falls into this.
